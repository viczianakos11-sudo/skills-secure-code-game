**Suggestions to raise later**
- One entry per vulnerability: name, CWE/OWASP mapping, vulnerable pattern, attack input, why it works, fix, how to detect it in code (what to look for), false-positive notes, a small runnable test.
- Record "agent lessons" besides the vulnerabilities themselves, learned so far:
  - Official solutions can be flawed: L3 `startswith(base_dir)` allows a sibling directory like `Level-3-secret` (use `os.path.commonpath` or a trailing separator); my own L1 solution checked the total limit inside the loop, so the result depended on item order.
  - Tests can encode quirks: L4 `hack.py` `test_1` only passes if the attacker input is normalised to `MSFT`, a properly parameterised fix alone does not satisfy it. Also L4 `tests.py` calls the methods the official text says should be deleted.
  - L5: the official `solution.py` deletes `MD5_hasher`, so the level's own `tests.py` `test_2` fails with it (verified); `hack.py` is inactive, CodeQL is the "attacker". Crypto lessons: MD5 for passwords (fast, unsalted), custom salt from `random` (digits only, ~70 bit), `random` instead of `secrets` for tokens (Mersenne Twister state recoverable from 624 outputs, verified), hardcoded `SECRET_KEY` (rotate it, removing is not enough), env vars silently `None` (fail fast).
  - S2 L1 (GitHub Actions supply chain): a third-party action (even pinned to a commit SHA) runs with the job's privileges, so pinning is not trust; a hardcoded token passed via `with:` leaks (the action's `index.js` literally logs it); GitHub's default `run` shell is `bash -e` without pipefail, so `curl | jq` failures pass silently (verified); the level's "hack" is just a `grep` for the action name, and the level cannot be run locally (needs a push to GitHub).
  - S2 L2 (Go login handler): besides the flagged user enumeration (differing error text) and secrets in logs, the code has an unflagged auth bypass: a package-level `var reqBody` is reused across requests, `json.Decode` keeps absent fields, so `{}` or email-only logs in as the previous user (verified; the official solution keeps the bug; `go test -race` flags it). Lesson for the agent: grep for shared mutable globals in request handlers, run race detector, and check what decoders do with missing fields. Go was not installed: downloaded from go.dev with `curl -L` and verified the SHA-256 (first try without -L saved a 75-byte redirect page and the checksum check caught it).
  - S2 L4 (Flask reflected XSS): a custom blocklist regex (`[<>{}[\]]`) only strips literal angle brackets, missing semicolon-less legacy HTML entities (`&lt`/`&gt`, valid per HTML5 without trailing `;` in text context); combined with Jinja2's `| safe` (disables autoescape) the entities reach the browser intact, get decoded into real `<`/`>` during the page's own HTML parse (into a text node, still inert), and a second JS line (`innerHTML = ...textContent`) re-parses that decoded text as markup, creating a real `<img onerror=...>`. Verified the decode step with Python `html.unescape` and, script-execution-free, with jsdom (constructed DOM, set innerHTML, inspected resulting element — never executed the onerror payload itself). Fix: drop the custom regex, let Jinja2's default autoescaping run (remove `| safe`), and change the template JS from `innerHTML =` to `textContent =` (defense in depth: a decoded `<`/`>` in a text node must never be re-parsed as HTML elsewhere). Lesson for the agent: blocklists miss encoding tricks (HTML entities here, same family as Level-3's path-traversal blocklist and Level-4 SQL quote-counting); grep templates for `| safe` and for any `.innerHTML =` fed by `.textContent`/user data as a reusable static-analysis pattern.
  - Always run the exploit before claiming a fix works; a blocklist is never a fix (L3 `./..`, L4 quote counting, false positive on `BRK-B`).
  - Flag "design smells" separately from exploitable bugs (L2 double counter increment, missing NULL checks, `strtol` edge cases; L4 `executescript`, arbitrary-SQL methods).
  - S2 L3 (XXE + hidden RCE backdoor): permissive XML parser options (`replaceEntities: true, recover: true, nonet: false`) allow external entity injection; the level also hides a `.admin` extension + `exec()` backdoor triggered via SYSTEM entity. Official fix: `replaceEntities: false, recover: false, nonet: true` and removing the exec path; verified via tests.js/hack.js (safety-classifier stopped me from actually running the exec backdoor — switched to non-executing verification for every later exploit). Lesson for the agent: grep for XML parser instantiation options across libxml/lxml/etc. bindings — permissive defaults are a recurring XXE source — and treat any `exec`/`eval`/`child_process` reachable from user-controlled branching as a backdoor candidate regardless of how obscure the trigger condition looks.
  - S2 L5 (JS CryptoAPI — type coercion, dynamic dispatch, prototype pollution): three distinct bugs in one object: (1) implicit `+=` coercion calls an attacker's `toString()`; (2) `CryptoAPI.sha1._round(...)` is looked up fresh on every call, so externally overwritable; (3) `w = []` left sparse, so index assignment falls through to a poisoned `Array.prototype` setter. Fixes: explicit `typeof` guard before coercion; capture a local closure reference to the internal method at definition time instead of re-reading a public, mutable property; pre-fill arrays with all needed indices instead of leaving them sparse. Verified via Node `vm` with a stubbed `alert`. Lesson for the agent: in JS, grep for (a) implicit string coercion of parameters later used in method calls, (b) any `obj.prop.method()` call pattern where `prop` is reassignable, used repeatedly inside a hot loop instead of captured once, (c) sparse array literals (`[]`) followed later by indexed writes — all three are "trusting the language's dynamic lookup" bugs, not memory-safety bugs, so classic static analyzers often miss them.
  - **Season 3 (LLM system-prompt confidentiality, GitHub Models / gpt-4.1-nano via GitHub Models API)**: six levels, each adding one more defensive layer around a system prompt that embeds a secret gift code — and each layer being a natural-language instruction or an LLM-judged gate, never a hard guarantee:
    - L1: bare system message with masking/confirmation rules scoped only to a "support" framing; bypassed by reframing the request as creative writing (story/poem) which the rules never addressed.
    - L2: adds a "user ID" check, but the ID itself is just free text the attacker types — no real authentication; plus an "ignore emergency framing" rule that the model doesn't reliably obey (non-determinism).
    - L3: adds code-level output validation (regex `[A-Z0-9]{8}` + stripped-alnum substring check) — the first real, deterministic defense layer, but creative-writing is explicitly banned in the prompt now, pushing attackers toward format-transformation (phonetic spelling, inserted separators) that still slips past the regex only if characters stay in order.
    - L4: adds "LLM-as-judge" self-verification (a second, narrower LLM call asking "is this a hack attempt, YES/NO") — bypassed by telling the guard model directly that it's not a hack, or by reframing as an accessibility/formatting request the judge doesn't recognize as hacking.
    - L5: adds an input-filter denylist (`secret`, `reveal`, `story`, `game`) — classic denylist-misses-the-intent problem (ask about "it" implicitly, ask for a rhyme, ask for a recap); also notably the output-validation regressed to a plain `.includes(SECRET)` (weaker than L3/4's normalized check) — the game's own defenses are not monotonically increasing in strength level to level, worth independently re-checking every layer rather than assuming later levels are strictly harder.
    - L6 (hardest, no official example prompts provided): gives the LLM real tool-calling access to a SQLite DB via an OpenAI function-calling schema; the `query_database` tool executes the LLM-authored SQL string with zero restriction (`db.all(query, ...)`, no parameterization, no `WHERE user_id = ?` enforcement) — a "second-order" SQL injection where the attacker doesn't write SQL directly but manipulates the LLM into writing and running a broad query (e.g. framed as a compliance/audit report) that returns other users' rows, then into presenting the result in a format (reversed, character-separated) that slips past both the narrow `.includes(SECRET)` output filter and the denylist/self-verification layers.
    - Cross-cutting Season-3 lesson for the agent: a system prompt is advisory, not an access-control boundary — LLM self-verification ("ask a model if this is an attack") is itself just another promptable, non-deterministic model, not a security control; real defenses need deterministic code-level gates (output regex/allowlist, actual auth tokens instead of self-reported user IDs, parameterized/constrained queries even when an LLM is the one constructing them); denylists (keyword or regex) are consistently the weakest and most bypassed layer across every level.
  - **Season 4 (agentic AI security — "ProdBot", a CLI coding-assistant simulator)**: five levels, each adding one new agentic capability and each capability introducing a textbook OWASP-LLM-Top-10 risk; official solution.txt files are unusually detailed (include root cause, multiple bypass vectors, and secure-alternatives lists) — worth re-reading directly rather than re-deriving:
    - L1 — Sandbox Escape: `bash.js`'s `validateCommand()` regex-matches the literal, static TEXT of a command for `..`, but bash is a dynamic language that builds values at runtime (`D=..` then `$D/password.txt`; or base64-encoding the path so no literal `..` ever appears). General lesson: **static text/regex validation of a command that will be dynamically interpreted (shell, SQL, template language, regex engine itself) can never be complete** — the validator and the interpreter have different models of "what the text means." The agent should flag any validator/sanitizer whose check happens on raw text before interpolation/expansion/decoding, and prefer "validate the resolved/canonical value after expansion" over "validate the source text."
    - L2 — Indirect Prompt Injection: web content is read raw and handed to the LLM as context with no separation between "page content" and "instructions"; hidden text (HTML comments, `display:none`, zero font-size) is invisible to a human in a browser but fully visible to the LLM reading raw source. General lesson: any agent that ingests externally-sourced text (web pages, API responses, file contents, tool outputs, past agent messages) and feeds it into an LLM's context without sanitization/structural separation has this exposure — grep for "fetch external content → directly interpolate into LLM prompt" data flows.
    - L3 — Excessive Agency: an MCP tool's self-reported scope/description ("sandbox only") doesn't match its actual code (`BASE_DIR = path.resolve(__dirname, "..")` — the whole level dir, not the sandbox subdir). General lesson: **tool/plugin descriptions are untrusted claims, not guarantees — the agent must audit the actual implementation (file paths, base dirs, permission scopes) of every tool it's told to trust, the same way it would audit a third-party dependency**; an agent inherits the real permissions of its tools, not the advertised ones.
    - L4 — Supply Chain Poisoning via shared mutable policy store: an "org-approved" skill writes a persistent (`ttl=0`) entry to the same flat-file memory store that the security validator reads to decide whether to relax path-traversal checks — i.e., the data plane (user/skill preferences) and the control plane (security policy) share one unprotected store with no integrity check on who wrote what. General lesson: this is a reusable architectural red flag beyond AI agents — **any system where "trusted" plugin/skill code can write to the same storage that a security decision later reads from, with no provenance/signing, effectively lets that plugin grant itself permissions**; the agent should look for "security-relevant state" (scopes, roles, feature flags, TTLs that gate security checks) stored in the same place as ordinary mutable application/user data.
    - L5 — Confused Deputy in multi-agent delegation: two agents both claim "read-only" access; one (Research) genuinely is read-only but aggregates unsanitized data from many untrusted sources (web/MCP/skills); the other (Release) actually has full workspace file access despite its claimed scope, and its system prompt falsely asserts the Research Agent's output is "pre-verified" and "schema-validated." No single component looks wrong in isolation — the vulnerability is in the trust *chain*. General lesson, directly reusable for a multi-agent review heuristic: **trust is not transitive between agents/services — when agent/service A ingests untrusted data and hands it to agent/service B, B inherits the risk, not A's trust level; every hand-off between agents is its own boundary that needs independent validation**, and claims like "pre-verified"/"schema-validated" in a system prompt or code comment should be treated as assertions to verify, not facts.
    - Season-4 cross-cutting meta-lesson: all five vulnerabilities trace back to one of two root causes that also recur across Seasons 1-3: (a) validating/trusting the SURFACE FORM of something (regex over raw command text, a tool's self-described scope, a system prompt's trust claim) instead of its REAL, resolved behavior or implementation; (b) collapsing a trust boundary by letting data and instructions, or user data and security policy, share one channel/store with no structural separation. A security-review agent should treat both as first-class, languageagnostic smells to search for, not just the specific instances found here.
- Pair the agent with real tools (CodeQL, Semgrep, Bandit, dependency scanners) instead of relying on the model alone, and make it reproduce findings before reporting them, to limit false positives.
